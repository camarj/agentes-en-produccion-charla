# T09 · API de chat — sesión 2026-09-23

## En pocas palabras
Ya existe la «ventanilla» del chat. El teléfono del asistente envía una pregunta a `POST /api/chat` y la respuesta llega **palabra por palabra**, como cuando alguien escribe en vivo. Antes de llamar al agente, el servidor revisa cinco cosas, en este orden:

| # | Revisión | Si falla | Ejemplo |
| --- | --- | --- | --- |
| 1 | ¿Tiene sesión y perfil completo? | 401 / 403 | Cookie vencida → «Tu sesión expiró…» |
| 2 | ¿El asistente está en pausa (kill switch)? | 423 | Raúl pausa todo desde el panel |
| 3 | ¿La pregunta tiene entre 1 y 1.000 caracteres? ¿Van menos de 10 en el último minuto? | 400 / 429 | Alguien pega un texto enorme o envía 11 seguidas |
| 4 | ¿Es su pregunta 31 o más? | 429 | Tope de 30 preguntas por persona en toda la charla |
| 5 | ¿Ya se gastó el presupuesto? | 423 (y pausa todo) | El coste estimado llegó a `PRESUPUESTO_MAX_USD` |

Si todo pasa, el agente responde. Al terminar, se suma el coste estimado de ese turno. Si el agente falla antes de escribir la primera palabra, el asistente ve «Tuve un problema técnico para responder. Tu pregunta quedó registrada para la sesión de preguntas.», y la pregunta pasa a la cola de Raúl (escalamiento `falla_tecnica`).

`GET /api/chat/historial` devuelve la conversación guardada, para que al recargar la página el chat aparezca como estaba.

## Desvíos
1. **Tope de 45 s, no 20 s** (Raúl, 2026-09-23). Anotado en la tarea.
2. **Sin reintento propio con el modelo de respaldo** (T05): el respaldo ya ocurre dentro de Mastra. El paso 11 quedó así: si el turno falla antes del primer token, se crea el escalamiento y se muestra el mensaje fijo. Anotado en la tarea.
3. **Qué cuenta como «falla antes del primer token»:** un error del modelo, el corte por los 45 s, un stream roto o un final sin texto, siempre que **no** haya sido un bloqueo de guardrail ni el cliente que se fue. Si el turno ni siquiera arranca, se hace lo mismo. Un error **después** de que salió texto se muestra como «La respuesta se interrumpió. Intenta preguntar de nuevo.». Nunca se muestra el texto técnico.
4. **Orden de las revisiones:** tal como la tarea (kill switch → validación → rate limit → contador → presupuesto). Consecuencias:
   - un mensaje inválido no gasta el rate limit;
   - una pregunta rechazada por el tope o por el presupuesto **sí** suma al contador (se incrementa antes de comparar).
5. **Presupuesto sin configurar:** si `PRESUPUESTO_MAX_USD` está vacío (como en `.env.example`), no hay tope de coste. **T14 debe fijarlo.**
6. **Migración nueva** `003_presupuesto.sql`. En una base existente hay que correr `pnpm db:migrate`; si no, la ruta de chat responde 500.
7. **Metadata en el `finish` de un bloqueo:** `toAISdkStream` agrega ese `finish` sin pasar por `messageMetadata`, así que `protegerStreamUI` completa el `trace_id` para que el pulgar funcione también en un mensaje bloqueado.
8. **Historial:** se usa `toAISdkMessages` (no `toAISdkV5Messages`, que es para AI SDK v5), y `trace_id` sale de `content.metadata.traceId` de cada mensaje guardado.

### T11 (UI de chat): contrato exacto
- **Petición:** `useChat` con el transporte por defecto (`DefaultChatTransport`, `api: '/api/chat'`). Envía `{ id, messages, trigger, messageId }`; la ruta usa **solo** el texto del último mensaje (`role: 'user'`, partes `text`). Se puede usar `prepareSendMessagesRequest` para mandar solo el último mensaje: el historial lo aporta la memoria. La cookie viaja sola (mismo origen).
  ```json
  { "messages": [{ "id": "u1", "role": "user", "parts": [{ "type": "text", "text": "¿Qué es el harness?" }] }] }
  ```
- **Respuesta 200:** stream SSE de AI SDK UI v7. Partes que llegan:
  - `start`, `start-step`, `finish-step`, `finish`;
  - `tool-input-start`, `tool-input-delta`, `tool-input-available`, `tool-output-available` (`buscar_laminas`, `escalar_pregunta`), útiles para mostrar «Buscando en las láminas…»;
  - `text-start`, `text-delta`, `text-end`;
  - `data-tripwire` si bloqueó un guardrail de entrada: mostrar `mensajeDeBloqueo(motivoDeTripwire(part.data))`;
  - `data-guardrail` si se reemplazó la salida: mostrar solo `MENSAJES_BLOQUEO.datos_personales`.
- **`trace_id` para el feedback:** `message.metadata.trace_id` del mensaje del asistente (llega en `start` y en `finish`). Luego `POST /api/feedback { trace_id, valor: 1 | -1 }`. Puede faltar si no hay observabilidad; en ese caso, ocultar los pulgares.
- **Falla técnica:** llega como un mensaje normal con el texto fijo (`MENSAJE_FALLA_TECNICA` en `lib/chat.ts`) y `finishReason: 'error'`. No hace falta lógica extra.
- **Errores antes del stream** (JSON `{ error, mensaje }`; mostrar `mensaje` tal cual):

  | Status | `error` | Qué hacer |
  | --- | --- | --- |
  | 400 | `mensaje_invalido` | Validar 1–1.000 caracteres también en el composer |
  | 401 | `no_autenticado` | Volver a la pantalla de entrada |
  | 403 | `falta_perfil` | Ir al formulario de perfil |
  | 423 | `mantenimiento` | Mostrar aviso de pausa; permitir reintentar |
  | 429 | `demasiados_mensajes` | Cabecera `Retry-After` (s); deshabilitar enviar |
  | 429 | `tope` | Deshabilitar el composer de forma definitiva |
  | 500 | `error_interno` | Mensaje genérico |

  Con `useChat`, estos llegan como `error` del hook: un `APICallError` (ai 7.0.112) con `statusCode` y `responseBody` = el JSON de arriba (también en `error.message`). Hacer `JSON.parse(error.responseBody).mensaje` y, si falla, mostrar un texto genérico.
- **Historial:** `GET /api/chat/historial` → `{ messages: UIMessage[] }` (v7: `id`, `role`, `parts`, y `metadata: { trace_id }` en las respuestas). Pasarlo como `messages` inicial de `useChat`. Detalles:
  - Una respuesta puede venir en **dos mensajes seguidos** del asistente (uno con la parte `tool-buscar_laminas` y otro con el texto); agrupar o mostrar solo los que tienen texto.
  - Un turno cancelado queda guardado con la respuesta a medias (así guarda Mastra).
  - Los turnos bloqueados en la entrada no aparecen.
- **Cancelar:** `stop()` de `useChat` corta la petición, y la ruta corta el agente (verificado en la traza).
