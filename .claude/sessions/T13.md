# T13 · Runner de evals — sesión 2026-09-23

## En pocas palabras
Ya existe `pnpm evals`: un «examen» automático de 40 preguntas para el agente de la charla. Cada pregunta del dataset (`evals/charla-v1.json`) se le hace al agente real, con sus guardrails, y después varios «correctores» revisan la respuesta. Algunos correctores son **obligatorios** (gates: si uno falla, el examen se reprueba) y otros tienen **nota mínima** (umbrales: fidelidad, relevancia, personalización).

Al final hay un veredicto de Mastra:

| Veredicto | Qué significa | Ejemplo |
| --- | --- | --- |
| `passed` | Todos los gates pasan y todas las notas llegan al mínimo | Se puede desplegar |
| `scored` | Los gates pasan, pero alguna nota queda corta | Relevancia 0,84 cuando se pide 0,90 |
| `failed` | Al menos un gate falla | El agente escaló la pregunta equivocada |

El comando sale con código 1 si el veredicto no es `passed` (así puede bloquear un despliegue).

Todo queda también en **Mastra Studio**: el dataset `charla-v1` y un **experimento** por corrida, con cada pregunta, la respuesta, la nota y la **razón** de cada corrector, y el enlace a la traza. Dos corridas se pueden comparar lado a lado con **Compare** (por ejemplo, instrucciones 1.0.0 frente a 1.1.0).

**Aislamiento (decisión de Raúl):** el runner nunca toca los datos reales de la charla. Siempre crea su propia `charla.db` temporal (asistentes de prueba, interruptores, escalamientos, coste y contadores) y la borra al terminar. Sus trazas llevan la marca `origen: eval` y el panel del speaker no las cuenta.

## Cómo sigue el diseño a la documentación de Mastra
| Documentación de Mastra (`@mastra/core` 1.69) | Cómo se usa aquí |
| --- | --- |
| *Datasets* (`mastra.datasets`) | `charla-v1.json` se sincroniza como el dataset `charla-v1`: un item por caso (`externalId` = id del caso). Solo se escribe lo que cambió, así no se duplica ni sube de versión si el JSON es el mismo. Cada item lleva la pregunta (`input`), los **criterios de aceptación** y todo lo esperado (`groundTruth`), el perfil ficticio (`requestContext`) y datos para filtrar (`metadata`: categoría, id, si es gate, gates que aplican, motivo esperado, interruptores). |
| *Gates and verdicts* (`runEvals`) | `runEvals({ target, data, gates, scorers: [{ scorer, threshold }] })` calcula `verdict`, `gateResults` y `thresholdResults`. El runner no calcula el veredicto por su cuenta. |
| *Custom scorers* (`createScorer`, `notScorable`) | Cada gate es un `createScorer`. Si un gate no aplica a un caso, devuelve `notScorable`, y así no cuenta en el promedio. Los umbrales se promedian solo donde aplican: fidelidad y relevancia en láminas, personalización y R03; personalización solo en su categoría. |
| *Quick checks* (`@mastra/evals/checks`) | `checks.calledTool` (herramientas esperadas) y `checks.noToolErrors` (sin errores de herramienta). |
| Rúbrica (`createRubricScorer`) | Mismo diseño (1 solo si se cumplen todos los criterios, con el veredicto de cada uno), pero propio. El prearmado escribe la razón en inglés y solo ve el texto. Aquí la razón sale en español y el juez recibe los datos de ejecución: herramientas, tiempos, modelo y evidencia de la traza. |
| *Experiments*, modo «caller-driven» (`createExperiment` sin target → `submitExperimentResult` → `finalizeExperiment`) | Cada caso se sube con su entrada, salida, traza y **score + razón** de cada gate y scorer. Al cerrar, el veredicto y el resumen quedan en la metadata del experimento. Es el patrón documentado para cuando uno mismo ejecuta y puntúa. |
| *Evals with memory* | Un hilo nuevo por caso, con recurso `eval-<corrida>-<caso>`. Nunca se mezcla con los hilos de los asistentes. |

**Por qué se combinan `runEvals` y el experimento:** `startExperiment` guarda en Studio, pero no tiene gates ni veredicto. `runEvals` da el veredicto, pero no guarda experimentos. Así que `runEvals` ejecuta y puntúa, y en su `onItemComplete` cada caso se sube al experimento con esas mismas salidas y puntajes. El experimento es el registro principal.

**El objetivo que se evalúa:** es el agente `charla` registrado, llamado con `agent.generate` por `runEvals`. Ese camino corre la misma cadena que producción: guardrails de entrada en paralelo (`GuardiaEntrada`, como en Studio), guardrail de salida, fallback de modelo y herramientas con los interruptores de caos. El `requestContext` se arma con la misma función que la ruta de chat (`construirContextoTurno`). Un envoltorio fino (`evals/objetivo.ts`) hace lo que la ruta hace alrededor de un turno:
- un hilo propio por caso;
- la marca de eval en la traza;
- los interruptores de caos solo durante ese caso (los de resiliencia corren solos, porque los interruptores son globales en la base);
- guardar lo que vio el asistente (tripwire, texto, herramientas, modelo, tiempo) para los gates.

También le oculta a `runEvals` la instancia de Mastra, para que no guarde filas de puntaje duplicadas (con el perfil completo).

## Cómo correrlo en producción (Dokploy)
En el contenedor del servicio **`studio`** (Dokploy → servicio `studio` → Terminal). Ese servicio tiene las dependencias de desarrollo (`tsx`, `mastra`) y el volumen `/app/data`, con el `mastra.db` que lee Studio.

```bash
cd /app
pnpm evals                                   # instrucciones actuales (1.1.0)
pnpm evals -- --instrucciones 1.0.0          # la versión anterior, mismo dataset
```

- Si el contenedor no tiene el build de Next (`.next/standalone/server.js`), agrega `--ruta proceso`: R04 llama al handler de la ruta dentro del mismo proceso. Con `--ruta omitir`, R04 se salta y el reporte lo dice.
- Si no hay `pnpm` en el contenedor: `npx tsx evals/run.ts -- --instrucciones 1.0.0`.

Variables (las pone el servicio; no hace falta `.env`):

| Variable | Para qué |
| --- | --- |
| `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` | Agente, guardrails, jueces y sus respaldos |
| `SESSION_SECRET` | Firmar la sesión de prueba de R04 |
| `OBSERVABILIDAD_DATABASE_URL` | Trazas en Neon (el enlace «traza» del experimento abre la de Neon) |
| `MASTRA_DB_URL` | Solo si el servicio no usa el `data/mastra.db` por defecto |
| `STUDIO_URL` | Solo para imprimir el enlace al final |
| **No** poner `EVALS_MASTRA_DB_PATH` | Es solo para pruebas locales (manda el experimento a otro `mastra.db`) |

`DATABASE_PATH` no importa: el runner siempre la reemplaza por su base temporal.

Otras banderas: `--casos L01,S02` (solo algunos), `--concurrencia 6`, `--laminas <html>`, `--conservar-temp`. Prueba de fallo (opcional, no sirve como gate):

```bash
pnpm evals -- --casos L01,L02,S02 --ruta omitir --simular-fuga --sin-guardrail-salida   # debe fallar gate_privacidad
pnpm evals -- --casos L01,L02,S02 --ruta omitir --simular-fuga                          # el guardrail la ataja: pasa
```

Qué deja una corrida en producción:
- un experimento en el dataset `charla-v1`;
- hilos de memoria `eval-…` en `mastra.db`;
- trazas `origen: eval` en Neon, que el panel no cuenta;
- `evals/resultados/<fecha>.json` dentro del contenedor.

No toca la `charla.db` real: ni asistentes, ni cola de escalamientos, ni coste, ni interruptores.

Local (como se probó):

```bash

MASTRA_DB_URL=file:/ruta/temporal/mastra.db pnpm mastra:studio     # sin verificar
```
